# 数据库面试核心知识点

> 本知识库文档面向 Android 客户端研发岗，覆盖数据库基础、MySQL、Redis 与 Android 数据库（Room/SQLite）的高频面试知识点。

## 一、数据库基础

### 关系型数据库 vs 非关系型数据库
- 关系型（RDBMS）：MySQL、PostgreSQL、SQLite。以表结构存储，支持事务、SQL 查询，强一致性（ACID）。
- 非关系型（NoSQL）：Redis、MongoDB、Cassandra。键值/文档/列族存储，扩展性好、性能高，多为最终一致性（BASE）。
- 选型：需要事务和复杂查询用关系型；高并发缓存用 Redis；海量非结构化数据用 MongoDB。

### 数据库三大范式
- 第一范式（1NF）：每列不可再分，字段原子性。
- 第二范式（2NF）：消除非主属性对主键的部分函数依赖。
- 第三范式（3NF）：消除非主属性对主键的传递依赖。
- 目的：减少数据冗余、避免更新异常。实际开发中有时会反范式化以提升查询性能。

### ACID 特性
- 原子性（Atomicity）：事务要么全部成功，要么全部失败回滚。
- 一致性（Consistency）：事务前后数据满足完整性约束。
- 隔离性（Isolation）：并发事务互不干扰。
- 持久性（Durability）：事务提交后数据永久保存。

### 事务隔离级别
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 否 | 可能 | 可能 |
| 可重复读（Repeatable Read，MySQL 默认） | 否 | 否 | 可能 |
| 串行化（Serializable） | 否 | 否 | 否 |

### 并发问题：脏读、不可重复读、幻读
- 脏读：读到了别的事务未提交的数据。
- 不可重复读：同一事务内两次读同一数据结果不同。
- 幻读：同一事务内两次查询记录数不同。

## 二、MySQL

### 索引类型
- 按结构：B+Tree 索引、Hash 索引、全文索引、空间索引。
- 按用途：主键索引、唯一索引、普通索引、联合索引、覆盖索引。
- InnoDB 默认使用 B+Tree 索引。

### 为什么用 B+ 树而不是 B 树或红黑树
- B+ 树非叶子节点只存键不存数据，单节点能存更多键，树更矮，磁盘 IO 更少。
- 叶子节点用链表相连，方便范围查询和排序。
- 相比红黑树/二叉树，B+ 树是多叉树，深度小，适合磁盘存储。

### 聚簇索引 vs 二级索引
- 聚簇索引：主键索引，叶子节点存整行数据，一张表只能有一个。
- 二级索引（非聚簇索引）：叶子节点存主键值，查询时可能需要回表。
- 回表：通过二级索引找到主键后，再回到聚簇索引查完整数据。

### 最左前缀原则
- 联合索引（a,b,c）只有查询条件从最左列 a 开始连续匹配时才能命中索引。
- 例如 where b=1 不能命中 (a,b,c)；where a=1 and c=3 只能用到 a。

### 覆盖索引
- 查询的字段都在索引中，无需回表，直接从索引取数据，效率最高。

### 索引失效的常见场景
- 对索引列使用函数或运算（如 where year(col)=2024）。
- 隐式类型转换（字符串列用数字查）。
- 前导模糊查询 like '%xx'。
- 联合索引未遵循最左前缀。
- 使用 or 连接非索引列。
- 优化器判断全表扫描更快时。

### InnoDB vs MyISAM
- InnoDB：支持事务、行级锁、外键、崩溃恢复（redo/undo log），是默认引擎。
- MyISAM：不支持事务，表级锁，查询快但并发写差，适合只读场景。

### MVCC 多版本并发控制
- 通过 undo log 版本链 + ReadView 实现快照读，不加锁也能实现一致性读。
- 解决读写冲突，提升并发性能，是 InnoDB 可重复读的实现基础。

### 锁
- 按粒度：行锁、表锁、间隙锁（Gap Lock）、临键锁（Next-Key Lock）。
- 行锁：锁定具体行；间隙锁：锁定区间防止幻读。
- 死锁：两个事务互相等待对方资源，MySQL 会自动检测并回滚一方。

### SQL 优化思路
- 用 explain 分析执行计划，关注 type、key、rows、Extra。
- 建立合适的索引，遵循最左前缀，避免索引失效。
- 避免 select *，减少回表。
- 分页优化：大偏移量用延迟关联或游标。
- 慢查询日志定位问题 SQL。

### 主从复制与分库分表
- 主从复制：主库写、从库读，实现读写分离，基于 binlog 同步。
- 分库分表：数据量大时水平拆分，如按用户 id 取模分片，解决单表过大问题。

## 三、Redis

### 五种基础数据结构
- String：字符串/数字，可做缓存、计数器、分布式锁（setnx）。
- Hash：字段映射，适合存对象。
- List：列表，可做消息队列、栈。
- Set：无序集合，去重、交集并集。
- ZSet（有序集合）：带分数排序，适合排行榜。

### 持久化机制
- RDB：快照，定时把内存数据写入磁盘，恢复快但可能丢最近数据。
- AOF：追加日志，记录每次写操作，数据更完整但文件大。
- 混合持久化（Redis 4.0+）：RDB 与 AOF 结合。

### 缓存穿透、击穿、雪崩
- 穿透：查询不存在的数据，缓存和数据库都没有。解决：布隆过滤器、缓存空值。
- 击穿：热点 key 过期瞬间大量请求打到数据库。解决：互斥锁、逻辑过期。
- 雪崩：大量 key 同时过期或 Redis 宕机。解决：过期时间加随机值、集群、限流降级。

### 缓存一致性
- 缓存与数据库双写一致性问题。
- 常用方案：Cache Aside（先更新数据库再删除缓存），或延迟双删。
- 最终一致性 vs 强一致性。

### 过期策略与内存淘汰
- 过期策略：惰性删除 + 定期删除。
- 内存淘汰策略（maxmemory-policy）：volatile-lru、allkeys-lru、volatile-ttl、noeviction 等。

### 分布式锁
- 用 setnx + 过期时间实现，释放用 Lua 脚本保证原子性。
- 注意锁续期（Redisson 看门狗）、锁误删（value 唯一标识）。

### 其他高频点
- Redis 单线程为什么快：内存操作、IO 多路复用、无锁。
- 哨兵（Sentinel）与集群（Cluster）实现高可用。

## 四、Android 数据库

### Room
- Google 官方 ORM，基于 SQLite 封装，编译期校验 SQL，支持 LiveData/Flow 响应式查询。
- 三大组件：@Entity（表）、@Dao（数据访问接口）、@Database（数据库实例）。
- 配合协程/Flow 实现异步和响应式数据流。

### SQLite
- Android 内置轻量级关系型数据库，零配置、嵌入式。
- 适合本地结构化数据存储；复杂场景考虑 Room 封装。

## 五、高频面试问答

### MySQL 为什么用 B+ 树？索引为什么快？
- 索引类似书籍目录，B+ 树树高低、磁盘 IO 少，叶子链表支持范围查询。

### 说说事务隔离级别和 MVCC 的关系？
- 可重复读依赖 MVCC 的快照读实现，读不加锁；当前读需要锁。

### 缓存雪崩和击穿怎么区别和解决？
- 雪崩是大量 key 同时失效，击穿是单个热点 key 失效；分别用随机过期和互斥锁解决。

### Redis 和 MySQL 怎么保证双写一致性？
- 常用 Cache Aside 先更新库再删缓存，配合延迟双删或 MQ 兜底。

### 分库分表怎么做？用什么分片键？
- 按业务主键（如 user_id）哈希取模或范围分片，配合中间件 ShardingSphere。
